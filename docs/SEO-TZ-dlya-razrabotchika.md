## 1. Цель и бизнес-контекст

### 1.1. Зачем SEO этому сайту

STREKOZA CAKES — индивидуальный кондитер в Гомеле. Заказ оформляется **не через корзину**, а через **Instagram Direct** `@strekoza_cakes_`.

SEO нужно, чтобы человек в Google/Яндекс по запросам вроде «торт на заказ Гомель», «муссовый торт Гомель», «моти на заказ Гомель» находил **сайт бренда**, понимал оффер и уходил в Direct.

Успех считается не «позициями ради позиций», а:

1. страница находится и корректно индексируется;
2. в сниппете понятно: что, где, как заказать;
3. на странице быстро находится CTA в Instagram;
4. условия (срок, предоплата, доставка) не вызывают сюрпризов.

### 1.2. Продуктовый оффер (равноправно 4 направления)

На текущем этапе все четыре направления имеют **равный приоритет** в текстах и структуре каталога:

1. **Корпусные пирожные**
2. **Муссовые изделия** (торт, бенто-торт, муссовые пирожные)
3. **Трайфлы**
4. **Моти**

### 1.3. Коммерческие правила (обязательно в контенте и FAQ)

| Правило | Формулировка для сайта |
|---------|------------------------|
| Срок (муссовые) | Муссовые изделия — только по предзаказу, **минимум за 3 дня** |
| Предоплата (муссовые) | За муссовые изделия — **предоплата 50%** после согласования |
| Доставка | **Не входит в стоимость** позиций. По Гомелю — Яндекс Доставка или самовывоз |
| Адрес | Улицу **не указываем**. Только город **Гомель** |
| Контакт | Instagram `@strekoza_cakes_` |

> Если для корпусных / трайфлов / моти сроки или предоплата отличаются — уточнить у заказчика и обновить FAQ. Пока в ТЗ жёстко зафиксированы правила для **муссовых**.

### 1.4. Бренд в метаданных и schema

- Публичное имя: **STREKOZA** / **STREKOZA CAKES**
- Instagram: https://www.instagram.com/strekoza_cakes_/
- Direct: https://ig.me/m/strekoza_cakes_
- Город: Гомель

### 1.5. Ориентиры рынка (не копировать, использовать для языка оффера)

Instagram-конкуренты/ориентиры: `novi.cake_`, `cake_me_gml`, `ttn.cakery`, `luvfrompiece`.  
У большинства нет полноценных сайтов → **сильный локальный лендинг — конкурентное преимущество**. Не нужно плодить десятки URL «как у крупного магазина».

## 2. Принятые решения (зафиксировано)

| Вопрос | Решение | Почему |
|--------|---------|--------|
| Структура | **Один лендинг** + якорные секции | Слабая конкуренция сайтов в Гомеле; заказ через Direct; быстрее внедрить |
| Язык | Только **RU** | Белорусский без редактора даст кривой UX и лишний `hreflang`-хаос |
| Стек | **Оставить Vite+React**; добавить пререндер | Смена на Next/Astro не обязательна, если build отдаёт HTML с контентом |
| Домен | Сейчас GitHub Pages; **позже свой домен** | Все абсолютные URL вынести в константу `SITE_URL` |
| Отзывы в schema | **Не добавлять**, пока блок «Скоро» | Фейковый `AggregateRating` = риск ручных санкций |
| Отдельные страницы товаров | **Фаза 2** | После своего домена и при росте спроса на узкие запросы |

## 3. Аудит текущего состояния (что уже есть / чего нет)

### 3.1. Что уже сделано хорошо

- HTTPS (GitHub Pages)
- `lang="ru"` в `index.html`

- Много изображений уже в **WebP**

- Контент вынесен в `src/content/site.ts` — удобно править тексты централизованно
- Есть `public/.nojekyll` для GitHub Pages

### 3.2. Критичные пробелы

| Проблема | Почему это важно | Что сделать |
|----------|------------------|-------------|
| SPA: в исходном HTML почти пустой `#root` | Робот/превью сначала видят «тонкую» страницу; Яндекс хуже дружит с JS-only контентом | Пререндер при `build` или иной способ отдать HTML с текстом |
| Нет `robots.txt` | Нет явных правил обхода и ссылки на sitemap | Добавить в `public/` |
| Нет `sitemap.xml` | Слабее сигналы для GSC/Вебмастера | Добавить (хотя бы на 1 URL) |
| Нет `rel=canonical` | Риск дублей (`/` vs `/index.html`, UTM и т.п.) | Добавить canonical на канонический URL |
| Нет Open Graph / Twitter Card | Плохие превью в мессенджерах/соцсетях | Добавить OG-теги + картинку |
| Нет JSON-LD | Нет расширенных возможностей сниппета (тип бизнеса, FAQ) | LocalBusiness/Bakery + ItemList/Product + FAQPage |
| H1 только после гидрации React | Без пререндера H1 может «не существовать» для части обходов | H1 в пререндеренном HTML, один на страницу |
| Семантика может быть на `div` | Роботам и a11y хуже понимать структуру | `header/main/nav/section/footer`, иерархия H2–H3 |
| Каталог визуально «муссово-центричный» | Бизнес хочет **4 равных** направления | Перегруппировать названия/описания/порядок акцентов |
| Нет блока FAQ | Упущенный интент + FAQ-сниппеты | Новый блок `#faq` |
| Условия 3 дня / 50% / доставка отдельно не выделены жёстко | Юридически-коммерческая прозрачность и SEO LSI | Обновить Conditions + FAQ + Order |

### 3.3. Важная особенность GitHub Pages project site

Сайт живёт не в корне домена, а по пути:

```text
https://havpen.github.io/StrekozaCakes/
```

В `vite.config.ts` уже есть:

```ts
base: process.env.GITHUB_ACTIONS ? '/StrekozaCakes/' : '/'
```

**Все** SEO-URL (canonical, og:url, sitemap, schema `url`) должны учитывать этот `base` на проде и легко меняться при переезде на свой домен.

## 5. SEO-карта лендинга (онпейдж)

### 5.1. Канонический URL

**Сейчас:**

```text
https://havpen.github.io/StrekozaCakes/
```

**Позже:** заменить на боевой домен заказчика, сохранив структуру лендинга.

### 5.2. Мета-теги (готовые формулировки)

**`<title>`** (ориентир ≤ 60–65 символов):

```text
STREKOZA — торты и десерты на заказ в Гомеле
```

**`<meta name="description">`** (ориентир 140–160 символов):

```text
STREKOZA CAKES — корпусные пирожные, муссовые изделия, трайфлы и моти на заказ в Гомеле. Самовывоз и доставка по городу (доставка отдельно). Заказ в Instagram Direct @strekoza_cakes_.
```

**Почему так:** в title — бренд + главный коммерческий интент + город. В description — 4 направления, гео, важное уточнение про доставку, канал заказа.

### 5.3. H1 (один на страницу)

```text
Корпусные пирожные, муссовые десерты, трайфлы и моти на заказ в Гомеле
```

Рядом (не вместо H1) можно оставить визуальный бренд **STREKOZA** (логотип / надпись классом, не вторым `<h1>`).

**Подзаголовок hero (поддержка):**

```text
Заказы по Гомелю через Instagram Direct. Декор выбираете вы — начинку и дату согласуем лично. Муссовые изделия — по предзаказу от 3 дней.
```

### 5.4. Карта секций, якоря, заголовки

| Якорь | Секция | Заголовок | Содержание (обязательное) |
|-------|--------|-----------|---------------------------|
| `#top` / hero | Первый экран | **H1** (см. выше) | CTA «Написать в Direct», ссылка на `#catalog`, город |
| `#catalog` | Каталог | **H2:** Что можно заказать | 4 направления равноправно; цены «от»; CTA в Direct |
| `#fillings` | Начинки | **H2:** Начинки и вкусы | Группы по типам изделий |
| `#order` | Как заказать | **H2:** Как заказать в Гомеле | 4 шага + акцент Direct |
| `#gallery` | Галерея | **H2:** Готовые заказы | Работы, alt с типом изделия |
| `#conditions` | Условия | **H2:** Условия заказа | 3 дня / 50% / доставка отдельно / самовывоз |
| `#faq` | FAQ (**новый**) | **H2:** Частые вопросы | 7 вопросов из п. 5.6 |
| `#reviews` | Отзывы | **H2:** Отзывы | Пока «Скоро» — без schema Review |

Иерархия: **один H1 → H2 секций → H3 только для подразделов** (карточки FAQ, шаги заказа).  
**Нельзя** использовать H2/H3 просто «чтобы текст был крупнее» — для размера шрифта только CSS.

### 5.5. Каталог: требования к равноправию 4 направлений

Сейчас в данных сильнее акцент на муссовой линейке. Нужно, чтобы пользователь и робот с первых экранов каталога видели **четыре опоры**.

Рекомендуемая логика представления (можно визуально группировать):

1. Корпусные пирожные  
2. Муссовые изделия (торт / бенто / муссовые пирожные — как подпункты одной группы или соседние карточки)  
3. Трайфлы  
4. Моти  

Для каждой карточки:

- понятное **коммерческое имя**;
- краткий `detail` (вес / от N шт);
- цена **от X BYN**;
- 1–2 предложения описания с естественным вхождением типа изделия + «на заказ» / «Гомель» где звучит нормально (без переспама);
- `alt` у обложки и слайдов разрезов.

Пример тона описаний (не копировать дословно обязательно, сохранить смысл):

- Муссовый торт: «Муссовый торт на заказ в Гомеле. Начинку и декор согласуем в Direct. Предзаказ минимум за 3 дня, предоплата 50%.»
- Корпусные пирожные: «Корпусные пирожные на заказ в Гомеле — набор под ваш повод.»
- Трайфл: «Трайфлы на заказ в Гомеле — удобный десерт порционно.»
- Моти: «Моти на заказ в Гомеле — набор от 4 шт.»

### 5.6. FAQ — готовые тексты

## 6. Техническая инфраструктура (обязательный минимум)

### 6.1. Константа базового URL

Создать единый источник правды, например `src/config/siteSeo.ts`:

```ts
export const SITE_URL = 'https://havpen.github.io/StrekozaCakes'
export const SITE_NAME = 'STREKOZA CAKES'
export const INSTAGRAM_HANDLE = 'strekoza_cakes_'
export const CITY = 'Гомель'
```

Все canonical/og/schema/sitemap собираются из `SITE_URL`.  
При переезде на домен заказчика меняется **одна константа** (+ `vite` `base`, если уходит с project pages).

### 6.2. `public/robots.txt`

Пример для текущего хостинга:

```txt
User-agent: *
Allow: /

Sitemap: https://havpen.github.io/StrekozaCakes/sitemap.xml
```

Пояснение: на статическом лендинге без `/admin` достаточно Allow /. Не закрывать CSS/JS.

### 6.3. `public/sitemap.xml`

Минимум одна запись:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
  <url>
    <loc>https://havpen.github.io/StrekozaCakes/</loc>
    <changefreq>weekly</changefreq>
    <priority>1.0</priority>
  </url>
</urlset>
```

После деплоя проверить, что URL открывается как XML, а не 404 GitHub Pages.

### 6.4. Favicon-набор

Сейчас есть `favicon.svg` (+ mark png). Желательно добавить:

- `favicon.ico`
- `apple-touch-icon.png` (180×180)
- ссылки в `<head>`

Это не «магия SEO», но влияет на доверие и аккуратность сниппетов/закладок.

### 6.5. Кастомная 404

Для project site на GitHub Pages добавить `public/404.html` (можно упрощённую копию лендинга или лёгкую страницу):

- текст «Страница не найдена»
- ссылка на `/StrekozaCakes/`
- ссылка на Instagram

Пояснение: GitHub Pages для 404 отдаёт `404.html` из корня published site.

### 6.6. Трейлинг слэш и дубли

Зафиксировать канон **со слэшем в конце** (как у GitHub Pages directory URL):

```text
https://havpen.github.io/StrekozaCakes/
```

Внутренние ссылки, canonical, sitemap — в одном стиле. Не плодить одновременно «правильные» ссылки с и без `/StrekozaCakes/`.

## 7. Семантическая вёрстка (DOM)

### 7.1. Целевая структура

```html
<body>
  <header>...</header>
  <main>
    <section id="hero">...</section>
    <section id="catalog">...</section>
    <section id="fillings">...</section>
    <section id="order">...</section>
    <section id="gallery">...</section>
    <section id="conditions">...</section>
    <section id="faq">...</section>
    <section id="reviews">...</section>
  </main>
  <footer>...</footer>
</body>
```

Навигация — в `<nav>` (можно внутри `header`).  
Карточки каталога допустимы как `<article>` внутри секции.

### 7.2. Правила заголовков

- Ровно **один** `<h1>`
- Секции — `<h2>`
- FAQ-вопросы / шаги — `<h3>`
- Не пропускать уровни ради стиля

### 7.3. Почему это в ТЗ

Поисковик и accessibility-инструменты читают смысл через структуру. «Красивые div с большим шрифтом» не заменяют заголовки. Регламент этапа 2 прямо требует замены бессмысленных обёрток на HTML5-секции и проверку иерархии.

## 8. Изображения и медиа

### 8.1. `alt`

У каждого смыслового `<img>` — осмысленный `alt` на русском.

Хорошо:

```text
Муссовый торт на заказ, начинка вишня и шоколад
Корпусные пирожные в разрезе, вкус персик
Моти набор, начинка нутела
```

Плохо: `img_0574`, `photo`, `image`, пустой alt у контентных фото.

Декоративные чисто UI-элементы (если появятся) — пустой `alt=""`.

### 8.2. Lazy-loading и LCP

- Герой / LCP-изображение: **без** `loading="lazy"`, желательно `fetchpriority="high"`
- Остальные изображения каталога/галереи: `loading="lazy"`
- Всегда указывать `width` и `height` (или стабильный aspect-ratio), чтобы не прыгал CLS

### 8.3. Форматы

WebP уже используется — сохранить. Не возвращать тяжёлые HEIC/исходники в прод.  
Видео `how-to-order.mp4` (если в первом экране/выше fold) не должно убивать LCP: постер, отложенная загрузка, не автоплей звука.

## 9. Структурированные данные (JSON-LD)

Добавить через `<script type="application/ld+json">` в пререндеренный HTML (или гарантированно в DOM до/при первом рендере так, чтобы попало в пререндер).

### 9.1. Организация / локальный бизнес

Тип: `Bakery` (или `LocalBusiness` + дополнительный тип).

Обязательные поля по смыслу:

- `@type`: `Bakery`
- `name`: `STREKOZA CAKES`
- `url`: канонический URL сайта
- `image`: абсолютный URL лого/обложки
- `address`: `{ "@type": "PostalAddress", "addressLocality": "Гомель", "addressCountry": "BY" }`  
  (**без** `streetAddress`)
- `areaServed`: Гомель
- `sameAs`: массив с Instagram URL
- `currenciesAccepted`: `BYN`
- при наличии телефона — `telephone` (сейчас можно не указывать, если его нет в публичном оффере)

Не выдумывать координаты, рейтинг, часы «с потолка». Если часов работы нет — не добавлять `openingHours`, пока заказчик не даст.

### 9.2. Каталог

Вариант A (проще): `ItemList` со списком позиций.  
Вариант B (лучше для товаров): отдельные `Product` + `Offer` для каждой позиции каталога.

Для `Offer`:

- `price` = число «от» (85, 55, 10…)
- `priceCurrency` = `BYN`
- `availability` = `https://schema.org/PreOrder` для муссовых (логично) или `InStoreOnly`/`LimitedAvailability` — выбрать один честный вариант и не врать про склад
- `url` = канонический URL лендинга (или URL с якорем `#catalog`, если решите; якоря в schema не обязательны)

### 9.3. FAQPage

Собрать из 7 пар вопрос/ответ раздела 5.6.

### 9.4. Чего не делать

- Не добавлять `Review` / `AggregateRating` без реальных отзывов на сайте
- Не указывать чужой адрес
- Не ставить `price: 0`
- Не копировать JSON-LD конкурентов

### 9.5. Проверка

После деплоя прогнать URL через:

- [Google Rich Results Test](https://search.google.com/test/rich-results)
- [Schema Markup Validator](https://validator.schema.org/)

## 10. Пререндер / индексация SPA (критичный пункт)

### 10.1. Проблема

Сейчас `index.html` содержит пустой `<div id="root"></div>` и подключает JS-бандл. Контент появляется только после выполнения JavaScript.

Google часто умеет рендерить JS, но:

- это медленнее и менее надёжно;
- Яндекс и некоторые превью-боты могут увидеть «пустую» страницу;
- title/description уже есть, но H1, тексты секций, FAQ и часть schema могут не попасть в первое представление.

### 10.2. Требование ТЗ

После `npm run build` опубликованный `index.html` (в `dist`) должен содержать **реальный текстовый контент** страницы: H1, ключевые секции, FAQ, ссылку на Instagram.  
Проверка: открыть `dist/index.html` без JS или через «View Page Source» на проде — текст виден.

### 10.3. Допустимые реализации (на выбор Dev)

Любой рабочий способ, совместимый с GitHub Pages:

1. Плагин пререндера для Vite (например, экосистема `vite-plugin-prerender` / аналог на Puppeteer/Playwright)  
2. SSG-подход без смены экосистемы, если команда уверенно внедрит  
3. Крайний упрощённый вариант: критический SEO-контент (H1, короткое описание, список позиций, FAQ, контакты) в статическом HTML внутри `#root` + hydrate React сверху — хуже по поддержке, но лучше чем пустой root

**Рекомендация:** полноценный пререндер маршрута `/` при CI build.

### 10.4. Что не считать решением

- «Google же рендерит React» — недостаточно для приёмки этого ТЗ  
- Только meta-теги без видимого контента в HTML

## 11. Производительность (Core Web Vitals)

Ориентиры после правок (PageSpeed Insights, мобильный):

| Метрика | Цель | Практические действия |
|---------|------|----------------------|
| LCP | ≤ 2.5s | hero `fetchpriority=high`, сжатый WebP/AVIF, не блокировать шрифтами |
| CLS | ≤ 0.1 | размеры картинок, резерв под шрифты/кнопки |
| INP | по возможности зелёный | не тяжёлые обработчики на главном потоке |

Уже хорошо: WebP, `display=swap`.  
Проверить:

- не грузить лишнее JS above-the-fold;
- тяжёлые карусели не должны блокировать первый рендер;
- сторонние виджеты (если появятся) — `defer`/`async`.

Цель по PSI: **90+ mobile желательно**, реалистичный минимум для приёмки — устранить красные LCP/CLS, связанные с нашими изображениями и вёрсткой.
